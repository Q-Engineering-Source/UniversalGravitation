## What the reference actually does

This is not a camera-following collision scheme. `EnumGravityDirection` has exactly `UP`, `DOWN`, `NORTH`, `EAST`, `SOUTH`, and `WEST`; every `adjustXYZValues` implementation is a signed coordinate permutation. Its per-direction hitbox constructors exchange the long player axis among world X/Y/Z and offset it around the eye/position anchor. For example, DOWN is a normal vertical AABB, NORTH extends in Z around eye height, and EAST extends in X (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/api/EnumGravityDirection.java:22-40,113-126,179-223,263-300,344-383,423-460`). This is a six-cardinal, world-axis-aligned construction, not an arbitrary quaternion-oriented bounding box (OBB), continuous surface normal, or radial gravity solver.

`GravityAxisAlignedBB` remains an `AxisAlignedBB`; it translates relative expansion/offset and the three collision-offset calculations through that selected cardinal basis (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/util/boundingboxes/GravityAxisAlignedBB.java:93-155`). Its `getOrigin()` returns the contact-facing anchor—min/max face centre as appropriate (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/util/boundingboxes/GravityAxisAlignedBB.java:179-193`). Thus the reusable observation is that vanilla AABB collision can support **cardinal** surface walking when all relative-axis operations agree. It does not establish that vanilla AABB collision can directly represent continuous ring-normal walking or a quaternion OBB.

The reference makes gravity direction, rather than look direction, the physical frame. It injects `EntityPlayerWithGravity` as the superclass of both `EntityPlayerMP` and `AbstractClientPlayer` (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/asm/Transformer.java:53-58`); that class forces a gravity-aware BB, converts moves/motion between absolute and relative coordinates, and maps `getEyeHeight` through gravity (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/asm/EntityPlayerWithGravity.java:116-145,184-203,471-536`). Therefore rendered view orientation is transformed to match the chosen physical direction; it is not evidence that arbitrary camera quaternion should drive collision.

## Collision, player semantics, and network hooks

The scope is broad because a real feet-on-face result is more than changing acceleration. The transformed player overrides `setPosition` to reconstruct the gravity-adjusted BB, redefines `resetPositionToBB` for asymmetric eye-compatible anchors, runs `jump()` with relative motion, redirects opaque-block checks using the BB origin, changes non-DOWN step sound, and computes the server fall-state block from a gravity-aware “below” location (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/asm/EntityPlayerWithGravity.java:223-263,325-353,463-469,539-554,640-675`). On a direction transition it preserves a centre-of-gravity/eye relationship, tries collision-safe relocation, and scales existing `fallDistance` (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/api/EnumGravityDirection.java:628-742`; `D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/capabilities/gravitydirection/GravityDirectionCapability.java:74-117`).

For normal movement/networking, it does not merely set `onGround`. `PatchEntityPlayerSP` repairs `onUpdateWalkingPlayer`'s `boundingBox.minY` assumption (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/asm/patches/PatchEntityPlayerSP.java:20-61`). `PatchNetHandlerPlayServer` changes `processPlayer` deltas and `handleFalling` to relative Y, and replaces hard-coded digging eye height `1.5` with `getEyeHeight()`—explicitly noting sneaking (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/asm/patches/PatchNetHandlerPlayServer.java:16-24,39-73,175-192`). The transformer also patches Entity/EntityLivingBase movement and jump, client position-look, world collision-box queries, EntityRenderer picking, rendering, and sound (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/asm/Transformer.java:59-80`). This is the relevant warning: physical orientation reaches walking, ground/fall, step, jump, crouch-sensitive interaction range, collision query, prediction, and server validation paths.

Its per-player capability stores current/previous/pending cardinal direction and transition state (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/capabilities/gravitydirection/IGravityDirectionCapability.java:11-59`; `D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/capabilities/gravitydirection/GravityDirectionCapabilityImpl.java:11-25,70-88`). It is attached to every player and serializes through Forge capability storage (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/capabilities/gravitydirection/GravityDirectionCapabilityEventHandler.java:23-57`); clone handling copies direction (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/listeners/GravityManagerCommon.java:156-175`). Server transition applies the state, calls `connection.update()`, and sends the direction to tracking players plus self (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/common/listeners/GravityManagerCommon.java:310-341`); clients request other-player state on join/tracking (`D:/WI - Dev Workspace/Up_And_Down_And_All_Around/src/main/java/uk/co/mysterymayhem/gravitymod/client/listeners/GravityManagerClient.java:83-99`). That establishes a server-owned, synchronized physical state—not a client camera-only state—as the pattern to retain.

## Implication for UG and the ring question

UG currently states that UIE solely owns Minecraft camera/input/picking/render Mixins, while `RevoUiSixDofCamera` is an adapter with a local orientation (`D:/WI - Dev Workspace/UniversalGravitation-src/UniversalGravitation/src/main/java/wi/unigrav/core/client/camera/RevoUiSixDofCamera.java:55-60`; `D:/WI - Dev Workspace/UniversalGravitation-src/UniversalGravitation/AGENTS.md:67,101`). Its active FREE attitude is a full quaternion `Q`, while field application remains client prediction only for an integrated server and dedicated-server field synchronization is still TODO (`D:/WI - Dev Workspace/UniversalGravitation-src/UniversalGravitation/src/main/java/wi/unigrav/core/client/ClientGravityTicker.java:20-35`; `D:/WI - Dev Workspace/UniversalGravitation-src/UniversalGravitation/.pensieve/knowledge/universal-gravitation-baseline/content.md:154-159`). Remote Boost also deliberately leaves the sole collision pass to native `EntityPlayerMP.move` (`D:/WI - Dev Workspace/UniversalGravitation-src/UniversalGravitation/src/main/java/wi/unigrav/core/boost/RemoteBoostServer.java:33-40`). Hence importing the reference’s old ASM player-superclass replacement, broad EntityRenderer/camera/picking hooks, or its GL/LWJGL-era hook stack would conflict with UG’s stated owner boundaries; those parts are not portable.

The re-usable reasoning is narrower: select an explicit, server-authoritative **physical upright/contact normal**; make the feet/eye anchors, motion basis, collision queries, fall/step/jump/sneak semantics, and synchronization consume that same state; and keep it distinct from the camera’s FREE Q. A block-face picker may provide a user-selected cardinal candidate, but a picked face or visual `Q` alone cannot turn native vertical collision into surface walking.

For a hollow rotating ring, the intended artificial acceleration is outward from the rotation axis and body-up is inward; its normal varies continuously around the ring. That is outside this reference’s six-cardinal AABB model. In particular, this note supplies no basis for claiming continuous radial walking, arbitrary OBB collision, Coriolis handling, or ring-station physics. A future design would need an explicitly authorized continuous-orientation collision/prediction/networking investigation and real-GPU acceptance.
